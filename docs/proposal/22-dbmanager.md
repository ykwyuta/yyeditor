# yydbmanager：複数DBのSQL実行・データ入出力・ER図・実行計画の可視化

作成日：2026-10-20。状態：初期実装中。操作と対応状況は[yydbmanager README](../../apps/yydbmanager/README.md)を参照。

## 1. 目的と要件

Windows向けの独立アプリ **yydbmanager** を追加する。SQL Workbench/J、pgAdminを参考に、SQLの編集・実行、結果の表示、データの入出力、スキーマの閲覧、ER図を一つの画面で扱う。特に、SQL Server Management Studio（SSMS）のように実行計画をグラフで読み解けることを中心機能にする。

| ID | 必須要件 | 設計箇所 |
|---|---|---|
| D1 | Oracle、SQL Server、PostgreSQL、SQLite、MySQL、IBM Db2、DuckDBに接続する | 3章 |
| D2 | SQLの編集・実行、複数結果セット、トランザクション、キャンセル | 4章 |
| D3 | yyシリーズ共通の同梱フォント UDEV Gothic を使う | 2・8章 |
| D4 | yysheetの資産を流用して大量の結果を格子表示する | 5・8章 |
| D5 | yyeditorの資産を流用してSQLを編集する | 4・8章 |
| D6 | yydrawの資産を流用してER図を表示する | 7・8章 |
| D7 | SSMS風の実行計画表示を重点実装する | 6章 |
| D8 | CSV、TSV、任意区切り文字、Parquet、COBOL固定長ファイルをインポート・エクスポートする | 9章 |
| D9 | SQLiteとDuckDBのエンジンを同梱し、別途インストールせず利用できる | 3・10章 |
| D10 | 他のyyシリーズからCIを分離する | 11章 |

段階的に実装するが、7種類のDBと全入出力形式は完成条件から外さない。初版の対象プラットフォームはWindows x64。SQL WorkbenchはSQL Workbench/Jを参考対象と解釈する。

参考ツールの役割は、[SQL Workbench/J](https://www.sql-workbench.eu/manual/using.html)のSQL中心の操作、[pgAdminのQuery Tool](https://www.pgadmin.org/docs/pgadmin4/latest/query_tool.html)の結果表示と計画閲覧である。参考製品の実装・アイコン・ファイル形式を複製する前提にはしない。

## 2. 画面と基本操作

- 左：接続先 → データベース／カタログ → スキーマ → テーブル・ビュー・列・索引・外部キー・ルーチンのツリー。項目は必要なときに読み込む。
- 中央上：接続・DB・スキーマと関連付けたSQLタブ。接続名とトランザクション状態を常時表示する。
- 中央下：「結果1・結果2…」「メッセージ」「実行計画」「実行履歴」をタブで切り替える。
- 右：選択中のテーブル・列・計画ノードのプロパティ。必要に応じて折り畳める。
- ER図とインポート／エクスポートの設定は専用タブで開く。SQLタブを閉じても別タブの結果や図は保持できる。
- ステータスバー：実行中／取得中／完了／停止、取得行数、DB実行・転送・描画の時間、未コミット状態。

SQLエディタ、結果格子、ツリー、プロパティ、ER図、実行計画、ダイアログは既存のフォント登録処理を共有し、既定をUDEV Gothicに統一する。DPIや文字サイズを変えても同じ文字計測を使う。

主要操作は「現在の文」「選択範囲」「スクリプト全体」の実行、「推定計画」「実測計画を付けて実行」「停止」「コミット」「ロールバック」。推定計画と実測計画は別操作にし、実測はSQLを実行することを操作名で明示する。

## 3. 接続方式とDBアダプター

### 3.1 接続方針

| DB | 提案する接続経路 | 配布・実装上の条件 |
|---|---|---|
| Oracle Database | ベンダーのODBCドライバーを使うアダプター | 利用者が対応クライアント／ドライバーを導入。サービス名・接続別名・認証方式を設定 |
| Microsoft SQL Server | Microsoft ODBCドライバー | SQL認証・Windows統合認証、暗号化・証明書検証を接続設定で扱う |
| PostgreSQL | Rustの専用クライアントを使うアダプター | TLS、パラメーター、取消要求、型情報を保持する |
| SQLite | 同梱エンジンの組み込み接続 | ファイル作成・既存ファイル・メモリDB・読み取り専用を扱う |
| MySQL | Rustの専用クライアントを使うアダプター | TLS、認証方式、複数結果セットを扱う |
| IBM Db2 | IBMのODBC／CLIドライバー | 初期の検証対象はLUW。z/OS・IBM iはメタデータ・権限・計画取得の個別検証後に対応を宣言する |
| DuckDB | 同梱エンジンの組み込み接続 | ファイル作成・既存ファイル・メモリDB・読み取り専用を扱う |

ODBCは接続経路を共通化するだけで、SQL方言・メタデータ・計画取得はDB別に実装する。Oracle／SQL Server／Db2の専用クライアントへの置き換えは、認証・型・取消の検証結果に応じた後続の選択肢とする。JDBCとJavaランタイムは必須にしない。

対応するサーバー版、ドライバー版、認証方式、TLS条件はアダプターごとの検証表として固定する。「接続できる」と「計画・型・入出力を検証済み」を分けて表示する。古いサーバーで取得できない情報は、未対応の理由と代替表示を出す。

### 3.2 共通インターフェース

`DbConnection`に接続テスト、文の実行、バインド、結果の逐次取得、次の結果セット、取消、トランザクション、メタデータ、計画取得を定義する。接続時に`Capabilities`を返し、推定計画・実測計画・一括投入・保存点・更新可能結果などの可否をUIに伝える。

接続情報にはDB種別、表示名、ホスト、ポート、DB／サービス、既定スキーマ、認証、TLS、タイムアウトを保存する。パスワードは既存のWindows資格情報ストアの処理を共通部品化して保管し、ワークスペース・SQL履歴・ログには含めない。統合認証では不要なパスワード欄を出さない。

同一接続ハンドルの操作は専用ワーカーで直列化する。SQLタブの実行セッションとメタデータ取得セッションを分け、補完によって実行中の接続を奪わない。SQLite・DuckDBのメモリDBなど、別接続では同じ状態を見られない場合は接続単位の共有・直列化に切り替える。一時テーブル・セッション変数・トランザクションは、そのSQLタブのセッションに属する。

## 4. SQL編集・実行

### 4.1 エディタの再利用

`yy-buffer`、`yy-core`、`yy-layout`、`yy-search`、`yy-syntax`を使い、既存Win32エディタから描画・IME・選択・検索・Undo/Redoを埋め込み可能な部品として抽出する。yyeditorのウィンドウを別プロセスで起動する方式にはしない。

SQL方言を接続先から選び、キーワード、文字列、識別子、コメントをハイライトする。スキーマ・テーブル・列名の補完、SQLテンプレート、選択範囲の整形、行・桁付きエラー位置への移動を備える。整形は方言の構文を保持できる範囲に限定し、未解釈の構文を改変しない。

### 4.2 文分割とパラメーター

セミコロンの単純分割は禁止する。文字列・引用識別子・コメント、PostgreSQLのドル引用、OracleのPL/SQLと単独行`/`、SQL Serverの単独行`GO`を方言ごとに解釈する。MySQLの`DELIMITER`はクライアント命令として処理する。`GO`等のクライアント命令をDBへ送信しない。解釈できないスクリプトには、選択範囲を一つのバッチとして送る操作を用意する。

名前付き入力パラメーターは、DBアダプターのプレースホルダーと型付きバインドへ変換する。文字列置換で値をSQLに埋め込まない。ストアドプロシージャの入出力パラメーター、更新件数、警告・通知、複数結果セットは対応能力に応じて扱う。

### 4.3 実行とトランザクション

- SQLタブごとに自動コミット／手動コミットを選び、初期値と変更後の状態を明示する。手動コミットでは未確定状態をタブとステータスバーに表示する。
- DBによるDDLの暗黙コミットや、ロールバックできない副作用は能力・文の種類に応じて説明する。全DBで同じロールバック動作を保証しない。
- 複数文の「エラー時に停止／続行」を設定する。文ごとの開始・終了・更新件数・エラーを記録する。
- キャンセルはドライバーの取消APIを使う。取消確認前に「停止完了」と表示しない。接続断で結果不明になった更新SQLは、自動再実行しない。
- SQL履歴は接続ID、SQL、時刻、結果要約をローカルに保存する。バインド値と結果データの記録は既定で無効にし、保存量と削除を設定できる。

## 5. 結果表示と正確な型

### 5.1 yysheetから再利用する範囲

格子描画、列幅、見出し、選択、コピー、仮想スクロール、表示範囲キャッシュ、列指向チャンク・一時ファイル・メモリ予算の仕組みを流用する。現在の`crates/yy-win/src/sheet/paint.rs`はシート状態に結び付いているため、読み取り用の`GridDataSource`を介する共通格子へ切り出す。

DBの結果をワークシートの数式として評価しない。`=...`から始まるDB文字列も文字列として表示・保存する。格子上の絞り込み・ソートには「取得済みの結果」が対象であることを表示し、DBへ追加SQLを送る操作と区別する。

### 5.2 DB値の保持

現在の`yy-sheet::Value`は数値を`f64`で持つため、DB結果の保管型にはそのまま使わない。別の`DbValue`／列チャンクで以下を保持し、格子には整形済みの表示と必要な生値を渡す。

- SQL NULL、空文字、空白文字列、空バイナリーを区別する。
- 符号付き／符号なし整数、大きな整数、精度・スケール付き任意精度十進数を桁落ちなく保持する。
- 浮動小数点、真偽、日付、時刻、タイムスタンプ、タイムゾーン情報、区間を区別する。
- Unicode文字列、バイナリー、JSON、UUID、DB固有型・配列等を型名付きで保持する。未対応型の文字列表現への変換は明示する。
- LOBは長さとプレビューを表示し、必要時に全文取得・保存する。接続を閉じる前に実体化できなかったLOBは、保存済みと扱わない。

Oracleの空文字とNULLなど、DB自体が同一視する値は区別を復元できないことを示す。表示形式を変えてもエクスポート用の生値を変えない。

### 5.3 大量結果・編集

結果はカーソルから一定行数／バイト数ずつ取得し、上限付きキューを経由して表示する。先頭ページ表示後もバックグラウンドで取得でき、メモリ上限を超える分は一時領域へ退避する。行数未確定時は「取得済み n 行」と表示する。

表示上限はエクスポート上限と分ける。「表示済み」「取得済み全体」「クエリーの全結果」を選択できる。実行済みカーソルを継続取得する場合と再実行する場合を明示し、再実行による結果変化を隠さない。長時間のスナップショット・ロックの保持は接続状態に表示する。

初期の任意SQL結果は読み取り専用。テーブルデータの編集は主キー／一意キーと元の値で対象行を特定し、変更をまとめてプレビューしてからパラメーター付きSQLで適用する。JOIN結果やキー不明の行を自動更新しない。更新競合は対象0行等から検出し、手動トランザクションと組み合わせる。

## 6. 実行計画の可視化（重点機能）

### 6.1 SSMS風の読み方

[SSMSのグラフィカル実行計画](https://learn.microsoft.com/en-us/sql/relational-databases/performance/display-and-save-execution-plans)を参考に、演算子アイコン、接続矢印、プロパティを備えた専用ビューを作る。初期表示は結果を左に置いて右から左へデータが流れる配置とし、上下方向も選べる。

- Scan、Seek、Join、Sort、Aggregate、Filter、Exchange、Materialize等を名前とアイコンで表す。DB固有の演算子名も併記し、意味を無理に共通化しない。
- ノードに対象テーブル／索引、推定行数、実測行数、実行回数、主要指標を表示する。選択時に述語、結合条件、索引条件、メモリ、I/O、並列処理、警告を詳しく表示する。
- 矢印の太さは推定／実測の行数で切り替える。極端な値には対数スケールと凡例を用意し、行数不明は別の線種にする。
- 推定と実測の乖離、スピル、DBが返した暗黙変換・索引候補・メモリ等の警告を強調する。アプリの推測は「分析上の指摘」と表示し、DBの警告と分ける。
- 検索、演算子種別の絞り込み、部分木の折り畳み、全体表示、ミニマップ、マウス位置を中心としたズーム、ノード間のキーボード移動を備える。
- 同じSQLの計画を並べ、演算子・対象オブジェクト・行数・時間の差を比較する。単純なノードID一致ではなく構造を照合し、不確かな対応は明示する。

SQLの該当箇所と計画内の文を相互に選択できるようにする。位置情報が返らないDBで、推測した範囲を正確な位置として示さない。複数文・複数計画・並列分岐・共有部分を扱い、一つの木に収まらない計画はDAGとして保持する。

### 6.2 正規化モデル

`PlanDocument`にDB種別・版、取得方法、推定／実測、対象SQL、取得時刻、生の計画を持つ。`PlanNode`は演算子、対象、述語、子／親参照、指標、警告、DB固有プロパティを持つ。各指標は値に加えて単位・由来・範囲（自身／部分木／文全体）、集約方法、取得できなかった理由を持つ。

コストはDB固有の評価値であり、ミリ秒として扱わない。SQL Serverのコスト比率も実測時間比率に置き換えない。部分木コストから自身のコストを算出する場合は二重計上・共有ノードを考慮し、算出不能なら未算出とする。

並列処理や包含時間のあるノード時間を単純加算しない。PostgreSQLのloops等、反復あたりの値と合計を区別する。DB間でコストや時間を同じ尺度として比較しない。取得できない実測値を0で埋めず「未取得」とする。

### 6.3 DB別の取得経路

| DB | 推定計画 | 実測・実行情報 | 注意点 |
|---|---|---|---|
| SQL Server | `SET SHOWPLAN_XML` | `SET STATISTICS XML`付きで実行 | XMLを直接解析し`.sqlplan`も開く。バッチ境界と設定の復元を管理し、SHOWPLAN結果と通常結果を識別する |
| PostgreSQL | `EXPLAIN (FORMAT JSON)` | `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` | ANALYZEはSQLを実行する。バージョン別の追加属性を保存する |
| Oracle | `EXPLAIN PLAN`と計画表の構造情報 | 対象のSQL ID・子カーソルの`V$SQL_PLAN`／統計、`DBMS_XPLAN.DISPLAY_CURSOR` | 権限・統計収集条件を診断。対象を識別せず「最後のSQL」の計画を使わない |
| MySQL | `EXPLAIN FORMAT=JSON` | サーバー版が対応する`EXPLAIN ANALYZE`形式 | 版によりTREE／JSON等が異なる。返却形式を能力判定して解析する |
| IBM Db2 | EXPLAIN表の演算子・ストリーム・オブジェクト情報 | LUWの対応可能な収集済み実測情報を追加 | EXPLAIN表・取得権限を確認。実測がなければ推定のみと明示する |
| SQLite | `EXPLAIN QUERY PLAN`の親子関係・詳細 | 実行全体の時間等。ノード統計は利用可能なビルド機能のみ | 詳細文字列の版差に備え、生データ表示にフォールバックする |
| DuckDB | 対応版の構造化EXPLAIN | JSONプロファイル／EXPLAIN ANALYZE | 同梱版に対して解析器を固定し、推定と実測を区別する |

根拠は[PostgreSQL EXPLAIN](https://www.postgresql.org/docs/current/sql-explain.html)、[Oracle DBMS_XPLAN](https://docs.oracle.com/en/database/oracle/oracle-database/19/arpls/DBMS_XPLAN.html)、[MySQL EXPLAIN](https://dev.mysql.com/doc/refman/8.0/en/explain.html)、[Db2のEXPLAIN機構](https://www.ibm.com/docs/en/db2/11.5?topic=facility-tools-collecting-analyzing-explain-information)、[SQLite EXPLAIN QUERY PLAN](https://www.sqlite.org/eqp.html)、[DuckDBのプロファイリング](https://duckdb.org/docs/lts/sql/statements/profiling)を参照する。SQLiteの表示形式は安定APIとみなさず、同梱版の固定と版別テストで対応する。

OracleのSQL MonitorやAWR等は初期の標準経路に含めず、追加時にはDB版・利用権限・ライセンス条件を個別確認する。EXPLAIN表が必要なDBでは、作成用DDLを表示し、通常の計画閲覧で自動作成・既存情報削除を行わない。

### 6.4 実測実行と保存

「実測計画を付けて実行」は、通常SQL実行と同じ副作用・ロック・負荷を持つ。ロールバックでシーケンスや外部処理まで元に戻るとは扱わない。対応するDBでは結果取得と実測計画を同じ実行で取り、計画のためにSQLを二重実行しない。EXPLAIN ANALYZEが通常の結果セットを返さないDBでは、その動作を明示する。

生XML／JSON／表形式と正規化データを、版付きの独自計画ファイルに保存できるようにする。SQL Serverの`.sqlplan`は原形式での保存にも対応する。図はSVG・PNGへ出力できる。原文・SQL・述語に機密値が含まれ得るため、共有用出力にはSQL・リテラル等の省略／置換と出力前確認を用意する。XML外部実体の読み込みは禁止し、入力サイズ・深さ・ノード数に上限を持つ。

## 7. ER図

DBのメタデータからテーブル、列、型、主キー、一意キー、外部キー、NULL可否、コメントを取得し、選択したスキーマ／テーブルのER図を生成する。複合キーと外部キーの列対応、自己参照、循環参照を保持する。外部キーから確定できない関連は自動で断定せず、手動の論理関連として追加できる。

`yy-draw`の座標系、カメラ、選択、接続点、配線、配置、グループ、保存・SVG／PNG出力を再利用する。ER専用のテーブル図形と列ごとの接続位置、カーディナリティ表示を追加する。DBメタデータと図上の位置・折り畳み・論理名は分けて保管し、再取得で人が整えた配置を失わない。

ダブルクリックでテーブル定義／データを開き、関連をたどってSQLのひな形を作れる。ER図の変更をそのままDBへ反映する機能は初期範囲に含めない。DDLを生成する場合は表示・保存までとし、通常のSQL実行として適用する。

## 8. 再利用と構成

### 8.1 既存資産と追加作業

| 資産 | 再利用 | 必要な変更 |
|---|---|---|
| `yy-buffer`／`yy-core`／`yy-layout`／`yy-search`／`yy-syntax` | SQLバッファ、編集、検索、文字計測、ハイライト | SQL方言・バッチ境界・DB補完を追加 |
| `yy-win/src/render.rs`、`ime.rs`等 | エディタ描画・IME | yyeditorのアプリ状態から埋め込み部品へ分離 |
| `yy-sheet`、`yy-win/src/sheet/paint.rs` | チャンク、一時領域、格子描画、選択・スクロール | DB型保持とデータソース抽象。`f64`変換を避ける |
| `yy-delimited`、`yy-encoding`、`yy-cobol`、`yy-sheet/src/fixed.rs` | 区切り形式、文字コード、コピー句、固定長・推定 | DB値との型変換、入出力診断を追加 |
| `yy-draw`、`yy-win/src/draw` | ER・計画の描画、カメラ、選択、配線、出力 | ER列ポート・計画ノード・DAG配置・専用操作 |
| `yy-jobs`、`yy-win/src/font.rs`、`credstore.rs` | 進捗・取消、共通フォント、資格情報 | 共通UI部品へ公開可能な範囲を抽出 |

現状のWin32部品は`pub(crate)`やアプリ状態への依存が多い。呼び出すだけで流用できるとは見積もらず、最初に共通化する。仮称`yy-ui-win`へフォント・格子・エディタ・図の埋め込み部品を段階的に抽出し、既存`yy-win`と新アプリの両方から使う。循環依存は作らない。

## 9. ファイルのインポート・エクスポート

### 9.1 共通の流れ

全形式で、テーブル／SQL結果 → 型付きレコードのストリーム → 変換 → ファイル、ファイル → 解析 → 型変換 → パラメーター付き投入を共通化する。表示格子の文字列を再読込して出力しない。全件をメモリに展開せず、進捗・取消・行数・バイト数・エラー位置を報告する。

ウィザードは形式、対象、列対応、型・NULL・文字コード等の設定、サンプルと問題一覧、実行の順。設定は名前付きプロファイルとして再利用できる。区切り・型・レコード長・固定長レイアウトの推定は補助にし、採用前に編集できる。

### 9.2 CSV・TSV・任意区切り文字

[RFC 4180](https://www.rfc-editor.org/rfc/rfc4180.html)のCSVは、カンマ、CRLF、二重引用符、引用符内の改行、`""`による引用符のエスケープ、任意の見出しを扱う。空白を勝手に除去しない。最終改行の有無を読めるようにする。

TSVと任意区切り形式はRFC 4180そのものとは表記せず、CSVと同じ引用・エスケープ規則を適用する方言として設定を保存する。任意区切りは1文字のUnicode文字（タブ、縦棒等）を対象とし、引用符・CR・LFとの衝突を禁止する。既存パーサーの単一バイト制約がある箇所は拡張する。既存システムの「引用なしTSV」も別プロファイルとして指定でき、区切りや改行を含む値はエラーにする。

UTF-8（BOM有無）、UTF-16、MS932、既存`yy-encoding`が扱う文字コードを選ぶ。CSVの標準プロファイルはUTF-8・カンマ・CRLFとし、LF等は互換プロファイルとして明記する。変換不能文字は既定でエラーとし、置換する場合は件数・位置を報告する。

CSV自体にはDBのNULLや型の規定がない。出力プロファイルでNULLマーカー、空文字との区別、引用規則、日付・小数・バイナリーの表現を決め、必要に応じて列型と設定をsidecarファイルへ保存する。たとえば未引用の`\N`をNULLとする場合、同じ文字列値は引用して区別するため、解析時に引用状態を保持する。汎用ツールとの交換でこの拡張を理解できない場合は、NULLと空文字の区別を保証できないことを事前表示する。

### 9.3 Parquet

Parquetのスキーマ・NULL・論理型を保持して読み書きする。[公式の物理型](https://parquet.apache.org/docs/file-format/types/)と[論理型](https://parquet.apache.org/docs/file-format/types/logicaltypes/)に沿い、整数・DECIMALの精度とスケール、日付・時刻精度、タイムゾーンの扱い、バイナリーを明示的にマッピングする。行グループ単位でストリーミングし、圧縮方式と行グループサイズを設定できる。

RustのParquet／Arrow実装を採用候補とし、版・ライセンス・MSRVを固定する。DuckDBによる読み書きだけに依存させず、任意DBの結果も同じ経路で出力する。入れ子型は対応DBなら構造を保持し、それ以外ではJSON化／列展開／拒否を選ぶ。黙って文字列へ落とさない。

### 9.4 COBOL固定長

`yy-cobol`のコピー句解釈とCodec、yysheetの固定長・マルチレイアウト機能を再利用する。

- レコード長と項目位置は**文字数ではなくバイト数**で定義する。区切りなし、CRLF、LF、EBCDIC NLを選べる。
- `PIC X`、`PIC 9`、符号付き・暗黙小数点、DISPLAY／ゾーン十進、COMP／バイナリー、COMP-3／パック十進などをCodecの対応範囲に基づき扱う。バイナリーのサイズ・バイト順は処理系プロファイルで固定する。
- MS932、EBCDICのCCSID等を指定する。日本語・DBCSでは変換後のバイト長を検査する。桁あふれ、丸め、文字切り捨て、表現不能値を既定でエラーにする。
- `OCCURS`、`REDEFINES`等は既存パーサーが扱える範囲を明示する。複数の01レコード等を一つのコピー句から完全解釈できるとは扱わず、複数の名前付きレイアウトと識別条件を設定する。
- マルチレイアウトでは種別列／条件 → レイアウト → DB列の対応を保存し、ヘッダー・明細・トレーラーを扱えるようにする。識別不能・条件重複・長さ不一致を行単位で報告する。
- 出力のFILLER、埋め文字、左／右寄せ、ゼロ埋め、符号位置、NULL代替を指定する。NULLを持てない形式への変換は明示的な規則を必須にする。
- レコード長・レイアウト推定は候補と信頼情報を表示し、採用後も人が編集できる。連続した文字領域の細かな項目境界は推定できない場合がある。

RDW／BDWを伴う可変長レコード、VSAMのコンテナー等は固定長ファイルとは別の追加範囲とする。必要な場合に通常の固定長として誤読しないよう検出・説明する。

### 9.5 投入・出力の完了条件

インポートは既存テーブルへの追加を基本とし、型付きバインドとバッチ投入を使う。新規テーブル作成では推定DDLを編集・確認できる。置換や更新／追加はキー・SQL・対象件数をプレビューする独立モードにする。

既定は一つのトランザクションで全件成功時に確定する。ただし非トランザクション表やDDL等の制約を事前に確認する。大規模投入ではチャンクごとの確定も明示的に選べ、成功・失敗・確定済み・未確定の件数を分ける。エラー行の隔離と続行は保存点等の能力に応じて実装し、取消時にどこまで確定したかを必ず残す。

エクスポートは同じフォルダーの一時ファイルへ書き、正常完了後に置き換える。取消・ディスク不足では既存の完成ファイルを壊さない。出力行数、列型、変換条件、変換エラー件数をレポートし、途中結果を全件出力済みと表示しない。全件件数のためだけに同じSQLを再実行しない。

## 10. SQLite・DuckDBの同梱と配布

両エンジンは必須機能として組み込み、開発機や配布先にCLI・ODBC・DBサーバーを要求しない。SQLiteはbundledビルド、DuckDBは組み込みC APIと対応するRustバインディングを候補とし、まず静的リンクを検証する。DuckDBのビルド時間・成果物サイズが大きい場合は、アプリ専用DLLを同梱する方式も許容する。どちらでも配布物だけでオフライン利用できることを必須にする。

[SQLiteのpublic domain方針](https://www.sqlite.org/copyright.html)、[DuckDBのMITライセンス](https://duckdb.org/faq)を確認し、採用版・バインディング・依存ライブラリごとのライセンス、NOTICE、ソース提供条件を記録する。Oracle等のベンダードライバーは同梱前提にせず、利用環境側で導入する。

同梱エンジンの版・ビルドオプション・ハッシュを配布マニフェストと「バージョン情報」に載せる。DuckDB拡張の自動ダウンロードを初期設定で無効にし、基本機能とParquet入出力がネット接続に依存しないことを確認する。DBファイルの更新互換性を検証し、古いエンジンへ戻せるとは保証しない。

既存yyシリーズの軽量exeのサイズ目標をそのまま適用せず、yydbmanagerのサイズ・起動時間・同梱エンジンのライブラリーサイズを別に測定する。

## 11. 専用CI

`.github/workflows/yydbmanager.yml`に専用のジョブ・キャッシュ・成果物・状態チェックを設ける。既存CIの`needs: agent`を継承せず、SSHエージェントのビルドを待たない。

- `push`／`pull_request`の対象パスは独立ワークスペース、専用ワークフロー、利用する共有クレート、フォント・ライセンス類とする。共有部品の変更時は既存CIと専用CIの両方を実行する。
- 以下のコマンドを独立側のワークスペースへ実行する。キャッシュキーは専用lockfileとエンジン版・対象環境から作る。
- 既存CIの`cargo ... --workspace`はDBクレートを含まない。専用の依存追加で既存側lockfileにDBドライバーを入れない。
- 共通化によるyyeditor・yysheet・yydrawの回帰は既存CIで確認し、独立側では共通UIの埋め込みとDBアプリを検証する。
- SQLite・DuckDBはすべてのPRで実機エンジンによる統合テストを必須にする。配布フォルダーだけを用いるオフライン起動・SQL・Parquetテストも実施する。
- PostgreSQL・MySQL・SQL Serverは専用CIの利用可能なサービス環境で実接続を検証する。Oracle・Db2は利用条件を確認した専用環境で定期／手動／リリース前に検証する。
- 実DBが使えないPRでは保存済み計画・メタデータ・プロトコル境界のテストを実行する。未実行の実DB試験を成功扱いせず、検証対象版ごとの結果をレポートする。リリースは必須の実DB試験を実施したコミットに限定する。
- 成果物は`yydbmanager-windows-x64`として個別に梱包し、同梱エンジン、必要なDLL、UDEV Gothic、NOTICE、操作説明を含める。既存yyシリーズの成果物とは分ける。

常時実行する軽量テストとDB別の重い試験はジョブを分けるが、実行計画・入出力・7DB対応の検証を省略して完成とはしない。

```powershell
cargo fmt --manifest-path apps/yydbmanager/Cargo.toml --all -- --check
cargo clippy --manifest-path apps/yydbmanager/Cargo.toml --workspace --all-targets --locked -- -D warnings
cargo test --manifest-path apps/yydbmanager/Cargo.toml --workspace --locked
cargo build --manifest-path apps/yydbmanager/Cargo.toml --release -p yydbmanager --locked
```

提案時点のCI用コマンド案。初期実装で対象manifestを追加済み（§14参照）。

以下は実装後に測る目標値であり、現時点の実測結果ではない。基準機（Windows x64、8論理コア、メモリ16GB、NVMe、表示倍率100%／150%）とDB・ドライバー版、データ、計測手順を記録する。
