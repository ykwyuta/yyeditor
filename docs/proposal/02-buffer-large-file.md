# 02. テキストバッファと巨大ファイル制御

## 1. 要求の整理

- 数 GB（目標 100 GB まで論理的に破綻しない）のファイルを、ファイルサイズに依存しない時間で開いて表示する。
- 開いた直後からスクロール・閲覧・編集ができ、行数の確定はバックグラウンドで行う。
- 編集（挿入・削除・全置換）の後もメモリ使用量が元ファイルのサイズに比例しない。
- Undo、バックグラウンド保存・検索のために安価なスナップショットが取れる。

## 2. データ構造の比較

| 方式 | 巨大ファイル | 編集コスト | スナップショット | 評価 |
|------|-------------|-----------|----------------|------|
| 全体を `String` / `Vec<u8>` に読み込み | × メモリ・読込時間がサイズ比例 | O(n) | O(n) コピー | 不採用 |
| ギャップバッファ | × 全読込が前提 | 局所編集は O(1) | O(n) | 不採用 |
| Rope（`ropey` 等） | △ 全文をヒープにコピーする必要あり | O(log n) | O(1)（Arc） | 不採用 |
| ピーステーブル（配列） | ○ 元ファイルを参照のみ | ピース数に比例 | O(ピース数) | 部分採用 |
| **永続ピースツリー（B+木, Arc 共有）** | ◎ 元ファイルを参照のみ | O(log n) | **O(1)** | **採用** |

## 3. 永続ピースツリーの設計

### 3.1 バッファソース

テキストの実体は次の 3 種類の「ソース」にあり、ピースはそれらへの (ソースID, オフセット, 長さ) 参照です。内部表現はすべて **UTF-8** です。

| ソース | 内容 | 実装 |
|--------|------|------|
| `Original` | 元ファイル（UTF-8/ASCII の場合）| `memmap2::Mmap`（読み取り専用） |
| `Transcoded` | 非 UTF-8 ファイルを UTF-8 に変換した一時ファイル | 一時ファイル＋ mmap（変換進行に応じて段階的にマップ） |
| `Add` | 入力・貼り付け・置換で追加されたテキスト | 追記専用のチャンク列（`Vec<Arc<[u8]>>`, 1 チャンク 64 KB〜）。巨大な貼り付け・全置換結果は一時ファイル化して `Transcoded` と同様に扱う |

追記専用なので、一度書いた領域は不変です。ピースやスナップショットがそれを参照し続けても安全です。

### 3.2 ツリー構造

```rust
pub struct Piece {
    source: SourceId,
    start: u64,        // ソース内バイトオフセット
    len: u32,          // 最大 1 MiB 程度に分割（下記）
    lf_count: LineCount,
}

pub enum LineCount { Known(u32), Unknown }

struct Node {                      // B+木（分岐数 16〜32）
    summary: Summary,              // 子の集約値
    kind: NodeKind,                // Internal(Vec<Arc<Node>>) | Leaf(Vec<Piece>)
}

#[derive(Clone, Copy)]
pub struct Summary {
    bytes: u64,
    lf: u64,                // 確定済み改行数
    unknown_bytes: u64,     // まだ改行数が未確定のバイト数
    // 拡張: CSV レコード数などはレイヤーで別途管理（04 章）
}

#[derive(Clone)]
pub struct Snapshot { root: Arc<Node>, sources: Arc<SourceTable> }
```

- 編集時はルートから葉までのパス上のノードだけを複製し（パスコピー）、それ以外のノードは `Arc` で旧版と共有する。1 回の編集で新規作成されるノードは O(log n) 個。
- **元ファイルは開いた時点で 1 MiB 単位のピースに分割**して木を作る。10 GB ならピース 約 1 万個、ノードは数百個で、メモリは 1 MB 未満。
  - 分割境界は UTF-8 の文字境界に合わせる（最大 3 バイト後退）。
  - 分割しておくことで、改行数を「ピース単位で」バックグラウンドで埋めていける。

### 3.3 行番号 ⇔ オフセット変換（行インデックスを持たない）

全行のオフセット配列（1 億行なら 800 MB）は持ちません。代わりに:

1. ツリーを `Summary.lf` で降りて、目的の行を含むピース（≤1 MiB）を O(log n) で特定。
2. そのピース内を `memchr` で改行走査（1 MiB なら数十 µs）。
3. 直近に参照した行位置を小さな LRU キャッシュに保持し、スクロールなど局所的なアクセスは差分走査で済ませる。

改行コードは内部では原文のまま保持します（CRLF/LF/CR 混在を保存時まで壊さない）。行分割の基準は LF と単独 CR を認識し、CR 単独ファイルのために `Summary` に `cr_only` カウントを持たせるオプションを用意します。

### 3.4 バックグラウンド行カウント（Indexer ジョブ）

```
open() ──► mmap ──► 1 MiB ピースに分割（lf_count = Unknown）──► 画面表示（先頭から）
                     │
                     └─► Indexer ジョブ: 各ピースを memchr_iter でカウント
                          → 一定量ごとに UI スレッドへ「ピース i..j の改行数」を送信
                          → UI 側で該当ピースの lf_count を Known に更新（木の再集約）
```

- `memchr` による改行カウントはメモリ帯域律速で 5〜10 GB/s 程度。実際にはストレージ読込速度（NVMe で 2〜7 GB/s、HDD で 0.2 GB/s 程度）が上限。
- **行数が未確定の間の表示**:
  - スクロールバーはバイト位置ベースで表示する（EmEditor と同様）。
  - 行番号は、確定済み範囲では正確な値、未確定範囲では「推定値」として薄く表示する。
  - 「指定行へ移動」は、未確定範囲に入る場合は必要なピースだけ同期的にカウントする（数百 MB/s 以上で走るため待ち時間は短い）。
- 編集によってピースが分割される場合、分割後のピースの改行数は未確定なら Unknown のまま引き継ぎ、確定済みなら分割部分だけ再カウントする。

### 3.5 長大行への対策

1 行が数 GB（改行を含まない JSON、ログ、固定長レコードデータなど）でも破綻しないように:

- レイアウト層は「論理行」をさらに最大 N 文字（既定 10,000 書記素）の **表示セグメント** に分割して扱う。折り返し OFF でも 1 回に計測・描画するのはセグメント単位。
- 水平スクロール位置は「論理行内のバイトオフセット＋セグメント内 x 座標」で保持する。
- EBCDIC 等の改行を含まない固定長レコードファイルは、レコード長を指定して「表示上の行」に分割できる（ファイルは変更しない）。

## 4. ファイルオープン処理

```
1. CreateFileW(FILE_SHARE_READ | FILE_SHARE_DELETE) で開く
   - 他プロセスによる書き込みを禁止（mmap 中の内容変化 = 未定義動作を防ぐ）
   - FILE_SHARE_DELETE は保存時に元ファイルを退避（rename）するために必要（06 章）
2. 先頭 64 KB（＋必要なら末尾）を読み、BOM / 文字コード判別（03 章）
3a. UTF-8 / ASCII → Original ソースとして mmap。即座に表示。
3b. それ以外 → Transcoder ジョブを起動（下記）。変換済みの先頭から表示。
4. Indexer ジョブ起動。区切り文字モードなら CSV Scanner ジョブも起動（04 章）。
```

### 4.1 非 UTF-8 ファイルの変換ロード（Transcoder）

- 元ファイルを 4 MiB 単位でストリーミングデコードし、`%LOCALAPPDATA%\yyeditor\tmp\<id>.u8` に UTF-8 で書き出す。
- 書き出しと並行して、変換済み範囲を順次ピースとして木に追加（`Transcoded` ソース）し、表示可能にする。変換速度は Shift_JIS→UTF-8 で 1 GB/s 程度を見込む。
- 変換中の編集は「変換済み範囲」に対してのみ許可し、未変換部への編集・保存・全文検索は変換完了を待つ（ステータスバーに進捗表示）。
- **ロスレス保証**: 元の文字コードで不正なバイト列（壊れた SJIS、未定義コードポイント）は、Unicode の私用領域（補助私用面 B の `U+10FE00`〜`U+10FEFF` の 256 文字に 1 バイトずつ対応）にエスケープして保持し、画面上は `\x81` のような特殊グリフで表示する。同じ文字コードで保存する際は元のバイトに復元されるため、**開いて保存しただけでファイルが変化しない**ことを保証する。
- 並列化: UTF-16/32 や自己同期可能な文字コードではチャンク並列変換、Shift_JIS 等は改行（0x0A は SJIS の 2 バイト目に出現しない）を同期点として並列化可能。ISO-2022-JP や EBCDIC の SO/SI のようなステートフル符号は、行（レコード）頭で状態がリセットされる前提で並列化し、前提が崩れた場合は逐次処理にフォールバックする。

## 5. メモリ使用量の見積もり（10 GB, 1 億行の UTF-8 ファイル）

| 項目 | サイズ |
|------|-------|
| ピースツリー（1 万ピース） | 約 0.5 MB |
| 行位置キャッシュ | 約 1 MB |
| 表示中の行のレイアウトキャッシュ | 数 MB |
| Add バッファ | 編集量に比例 |
| mmap されたページ | OS のページキャッシュ（プロセスの Private Bytes には計上されない） |

## 6. 外部変更の検出

- 開いたファイルは書き込み共有を拒否しているため、通常は他プロセスから変更されない。
- 共有を許可して開く設定（ログファイルの追跡用途など）を選んだ場合は mmap を使わず、`ReadFile` ベースのチャンクキャッシュを使うソース実装に切り替える（`BufferSource` trait で抽象化）。`ReadDirectoryChangesW` で変更を検知し、再読込・追記分の自動取込（tail モード）を提供する。
