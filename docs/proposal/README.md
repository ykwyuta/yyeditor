## 2. 提案の要点（サマリ）

1. **コアとUIを完全に分離した Cargo ワークスペース構成。**
   バッファ・文字コード・検索・CSV などのコアは OS 非依存のライブラリクレートとし、Linux CI でもテスト可能にします。Windows 固有部分は `yy-win` クレートに閉じ込めます。

2. **GUI は Win32 API ＋ Direct2D / DirectWrite によるネイティブ実装**（`windows` クレート使用）。
   汎用 GUI フレームワークは「数 GB のテキストを仮想スクロールで描く独自コントロール」と「日本語 IME のインライン変換」に対する制御が弱いため採用しません。バイナリは数 MB、起動は 100ms 未満を目標とします。

3. **巨大ファイルは「メモリマップ ＋ 永続（イミュータブル）ピースツリー」で扱う。**
   元ファイルはコピーせず `mmap` で参照し、編集差分だけを追記バッファに持ちます。ツリーの各ノードにバイト数と改行数を集約するため、行番号→オフセット変換は O(log n) で、全行分のインデックスを持つ必要がありません（10 GB のファイルでも管理メモリは数 MB）。
   ノードを `Arc` で共有する永続構造のため、**スナップショットが O(1)** で取れ、Undo・バックグラウンド保存・検索・自動バックアップがすべて同じ仕組みで実現できます。

4. **内部表現は常に UTF-8。** UTF-8 / ASCII のファイルは mmap をそのまま参照（ゼロコピー）、それ以外の文字コードはバックグラウンドで UTF-8 の一時ファイルへストリーミング変換し、それを mmap します。変換中も変換済みの先頭部分から表示・閲覧可能です。変換できないバイトはロスレスに保持し、保存時に元のバイトへ戻します。

5. **文字コードは自前の `yy-encoding` クレートに集約。** `encoding_rs` を土台に、JIS X 0213（Shift_JIS-2004 / EUC-JIS-2004）、CP932 と JIS の差異（波ダッシュ問題など）、ISO-2022-JP 系各種、EBCDIC 系（CCSID 290/930/939/1390/1399 ほか）をテーブル駆動で実装し、ベンダー固有コード（JEF/KEIS 等）は外部マッピングファイルで追加できる設計にします。

6. **CSV は「レコードインデックス＋引用符状態チェックポイント」で巨大ファイルでも正しく扱う。**
   フィールド内改行によって「行 ≠ レコード」になる問題を、ファイル走査時に CSV 状態機械の状態をチェックポイントとして記録することで解決します。編集で引用符の対応が崩れた場合も、状態が既存チェックポイントと一致（収束）した地点で再走査を打ち切る差分再計算を行います。

7. **正規表現は `regex` クレート（線形時間保証）を標準、後方参照・先読みが必要な場合のみ `fancy-regex` にフォールバック。** 巨大ファイルの全置換は数百万個のピースを生成せず、新しい一時ファイルへストリーミング出力して 1 つの Undo 単位として差し替えます。

8. **保存は常に「一時ファイルへ書き出し → 原子的差し替え」。** 文字コード変換時は事前に変換不能文字を検査して一覧表示し、中止／代替文字／数値文字参照などを選択できます。拡張子変更で CSV→TSV のような区切り文字変換も行えます。

9. **矩形選択とマルチカーソルは同じ「一括編集」経路で処理する。**
   矩形は表示桁（全角=2、タブ展開後）で定義して行ごとの範囲を遅延展開するため、100 万行の矩形でも選択・スクロールは表示範囲分のコストのみです。全カーソル分の編集は 1 つのスナップショット（= 1 回の Undo）として適用し、巨大な矩形の編集は全置換と同じストリーミング方式に切り替えます。CSV モードではセル範囲の矩形選択になります。

10. **シンタックスハイライトは独自の軽量エンジン（宣言的な TOML 定義＋状態機械）で行う。**
   拡張子・ファイル名・先頭行などでファイル種類を判定します。行をまたぐ状態（ブロックコメント等）は CSV と同じ「状態チェックポイント＋収束判定」で管理するため、数 GB のファイルでも表示範囲だけを処理して即座に色付けでき、入力時の再処理も数行で済みます。COBOL・JCL のような固定桁形式にも対応します。

11. **リモート編集は「組み込み SSH ＋ 接続先エージェント」で行う。**
   VS Code の Remote - SSH と同様に接続先へ小さなエージェント（`yy-agent`）を送り込みますが、SSH は `ssh.exe` を使わず exe に組み込んだ Pure Rust 実装（`russh`）で話すため、端末側は OpenSSH に依存しません。編集（ピースツリー）は手元に持って入力の応答を回線遅延から切り離し、バイトの実体は接続先に置いたまま表示範囲だけを取り寄せます。ソースが追記専用であることを利用してスナップショットを接続先に再構成し、保存・検索・Grep・文字コード変換を接続先で実行するため、10 GB のファイルの 1 行修正も数 KB の転送で保存できます。

## 4. 性能・品質目標（抜粋）

| 項目 | 目標値 |
|------|-------|
| 起動（空ウィンドウ表示まで） | 100 ms 未満 |
| 10 GB の UTF-8 ファイルを開き最初の画面を表示 | 0.5 秒未満（ファイルサイズに依存しない） |
| 10 GB の全行数確定（NVMe SSD） | 5 秒程度（ディスク読み出し速度律速、バックグラウンド） |
| 10 GB ファイル閲覧時の常駐メモリ | 100 MB 未満（OS のページキャッシュを除く） |
| 1 文字入力から再描画まで | 16 ms 未満（ファイルサイズに依存しない） |
| 実行ファイルサイズ | 10 MB 未満（外部ランタイム不要の単一 exe） |
