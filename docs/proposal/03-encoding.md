# 03. 文字コード対応

## 1. 対応文字コード一覧

### 1.1 Unicode 系

| 名称 | 備考 |
|------|------|
| UTF-8（BOM なし / あり） | 既定。不正バイト列を含むファイルもロスレスに扱う |
| UTF-16LE / UTF-16BE（BOM あり / なし） | サロゲートペア対応。不対サロゲートもロスレス保持 |
| UTF-32LE / UTF-32BE | |
| CESU-8 / Modified UTF-8 | Java・Oracle 由来データ用（オプション） |

### 1.2 日本語 レガシー（JIS 系）

| 名称 | 主な差異・備考 |
|------|---------------|
| **Shift_JIS（JIS X 0208 準拠）** | 0x815F→U+005C、0x8160→U+301C（波ダッシュ）等の JIS 準拠マッピング |
| **CP932（Windows-31J）** | NEC 特殊文字、NEC 選定 IBM 拡張、IBM 拡張文字。0x8160→U+FF5E（全角チルダ）等の Microsoft マッピング |
| Shift_JIS-2004（JIS X 0213） | 第3・第4水準漢字、結合文字（か゚ 等、2 コードポイントへ対応） |
| **EUC-JP** | JIS X 0208 / 0201 カナ（SS2）/ 0212 補助漢字（SS3） |
| eucJP-ms | CP932 互換の拡張（ユーザー定義文字・IBM 拡張） |
| CP51932 | Microsoft 版 EUC-JP |
| EUC-JIS-2004 | JIS X 0213 |
| **ISO-2022-JP（JIS）** | RFC 1468。メールで使用 |
| ISO-2022-JP-1 / -2 / -3 / -2004 | 補助漢字・JIS X 0213 |
| CP50220 / CP50221 / CP50222 | Microsoft 版 ISO-2022-JP（半角カナの扱いが異なる） |
| JIS X 0201（ASCII＋半角カナ 8bit） | 古いシステム出力 |

### 1.3 EBCDIC 系（メインフレーム）

| 名称 | 備考 |
|------|------|
| IBM CCSID 037 / 500 / 1047 | 英語 EBCDIC |
| **IBM CCSID 290 / 1027** | 日本語 1 バイト（290 = カタカナ拡張、1027 = 英小文字拡張） |
| **IBM CCSID 930 / 5026** | 290 ＋ DBCS（300/4396）、SO(0x0E)/SI(0x0F) で切替。カタカナ系 |
| **IBM CCSID 939 / 5035** | 1027 ＋ DBCS。英小文字系 |
| IBM CCSID 1390 / 1399 | 930/939 に JIS X 0213 相当の拡張と €記号を追加 |
| EBCDIK（日立・NEC 等の英小文字なしカナ EBCDIC） | 1 バイト系 |
| 富士通 JEF / 日立 KEIS / NEC JIPS(E) | ベンダー漢字コード。**外部マッピングファイル方式**で対応（下記 4.3） |

### 1.4 その他

- ISO-8859-1〜15、Windows-1250〜1258、KOI8、GB18030、Big5、EUC-KR 等は `encoding_rs` 経由で対応（海外データの閲覧用）。
- Windows のコードページ（`MultiByteToWideChar`）に存在する任意の文字コードを「システムコードページ」として選択可能にする（検証済みリスト外の文字コードへの逃げ道）。

## 2. コーデック設計（`yy-encoding` クレート）

### 2.1 トレイト

ストリーミング（チャンク単位）で、状態を持つ符号（ISO-2022-JP、SO/SI）に対応できるインタフェースにします。

```rust
pub trait Encoding: Send + Sync {
    fn name(&self) -> &'static str;            // "Shift_JIS", "IBM-930" ...
    fn aliases(&self) -> &'static [&'static str];
    fn new_decoder(&self, opts: &DecodeOptions) -> Box<dyn Decoder>;
    fn new_encoder(&self, opts: &EncodeOptions) -> Box<dyn Encoder>;
    fn properties(&self) -> EncodingProps;     // 自己同期性、改行バイト、最大バイト長、ステートフルか
}

pub trait Decoder: Send {
    /// src を UTF-8 として dst に追記。途中で切れたマルチバイト列は内部に保持。
    fn decode(&mut self, src: &[u8], dst: &mut Vec<u8>, last: bool) -> DecodeResult;
    fn reset(&mut self);                       // 行頭・レコード頭での状態リセット
}

pub trait Encoder: Send {
    fn encode(&mut self, src: &str, dst: &mut Vec<u8>, last: bool) -> EncodeResult;
}

pub enum Unmappable {           // 保存時に変換できない文字の扱い
    Error,                      // 位置を報告して停止（既定）
    Replace(char),              // '?' や '〓' に置換
    NumericCharRef,             // &#x20BB7; 形式
    Escape,                     // \u{20BB7} 形式
}
```

### 2.2 実装バックエンド

| バックエンド | 対象 |
|------------|------|
| `encoding_rs` ラッパー | UTF-8/16、WHATWG 定義の Shift_JIS（=CP932 相当）、EUC-JP、ISO-2022-JP、欧州・アジア各種 |
| 自前テーブル駆動実装 | JIS 準拠 Shift_JIS、JIS X 0213 系、eucJP-ms、CP51932、ISO-2022-JP-1/2/3/2004、CP5022x、EBCDIC 全般、UTF-32、CESU-8 |
| 外部マッピングファイル | JEF / KEIS / JIPS、ユーザー定義文字（外字）の追加 |
| Windows API（`MultiByteToWideChar`） | その他のシステムコードページ（フォールバック） |

`encoding_rs` は WHATWG 仕様準拠のため、「Shift_JIS」が実際には CP932 のマッピングであり、JIS X 0213 や ISO-2022-JP の亜種にも対応していません。日本の業務データでは **CP932 と JIS 準拠の違い（波ダッシュ・全角チルダ、全角マイナス、¢£¬ 等）** が頻繁に問題になるため、これらは自前テーブルで明示的に区別します。

### 2.3 テーブル生成

- `tools/gen-tables` が、Unicode Consortium の対応表、JIS X 0213 の対応表（x0213.org 公開データ）、IBM の CDRA 変換表（ICU の `.ucm` ファイル）などを入力に、Rust のソース（`static` 配列）を生成して `crates/yy-encoding/tables/` にコミットする。
- デコード用は「リード バイト→ 256 要素のページ」の 2 段テーブル、エンコード用は Unicode の上位バイトで引く 2 段テーブルとし、ともに O(1) 変換。
- 実行時に外部 `.map` ファイル（TSV 形式: `バイト列<TAB>Unicode`）を読み込んでテーブルを上書き・追加できる。外字（ユーザー定義文字、SJIS 0xF040〜0xF9FC → U+E000〜）もこの仕組みで対応する。

### 2.4 ロスレス往復の保証

| 状況 | 扱い |
|------|------|
| UTF-8 ファイル中の不正バイト列 | 元ファイルを直接 mmap しているのでバイト列はそのまま保持。表示時のみ `\xNN` グリフで描画 |
| レガシー文字コード中の不正バイト / 未定義コード | 私用領域 `U+10FE00+byte` にエスケープ（02 章）。同じ文字コードで保存時に元バイトへ復元。**別の文字コードで保存する場合は変換不能文字として報告** |
| 1 対多・多対 1 マッピング（例: CP932 の NEC 選定 IBM 拡張と IBM 拡張の重複） | デコード時にどちらの符号だったかを失わないよう、重複符号はエンコーダで「優先符号」を設定可能（既定は IBM 拡張優先 = Windows 標準と同じ） |
| ISO-2022-JP のエスケープシーケンス冗長性 | 完全な同一バイト往復は保証しない（意味的等価）。保存時にエスケープの出し方を正規化する旨を UI に表示 |

エスケープ用私用領域の文字が元ファイルに本当に含まれている場合（UTF-16/UTF-32 で読み込んだファイル等）は、デコーダがドキュメント単位でエスケープ無効フラグを立て、衝突を防ぎます。

## 3. 文字コードの自動判別

### 3.1 判別手順

```
1. BOM 判定                       → UTF-8 / UTF-16LE/BE / UTF-32LE/BE で確定
2. ファイルタイプ設定・ユーザー指定・最近開いたファイル履歴 → あれば採用
3. 先頭 64 KB（大きいファイルは先頭・中央・末尾の各 64 KB）をサンプリング
4. UTF-16/32（BOM なし）判定      → 0x00 の出現位置の偏り（偶数/奇数）で判定
5. ESC $ B / ESC ( J 等を含み 8bit バイトがない → ISO-2022-JP 系
6. UTF-8 として完全に妥当         → UTF-8（ASCII のみなら設定の既定値）
7. 日本語候補のスコアリング        → Shift_JIS / CP932 / EUC-JP / EBCDIC(930/939)
8. 最終候補を chardetng の結果と照合、確信度が低ければステータスバーで警告
```

### 3.2 日本語スコアリング

- 各候補でデコードを試み、エラー数・未定義コード数で足切り。
- 残った候補について、デコード結果の文字種分布（ひらがな・カタカナ・常用漢字・JIS 第1水準の出現率、半角カナの連続、制御文字の出現）を点数化。
  - 例: EUC-JP を Shift_JIS と誤判定すると半角カナと第2水準漢字が不自然に多くなる。
- Shift_JIS と CP932 の区別は、CP932 拡張領域（0x87, 0xED〜0xEE, 0xFA〜0xFC）の出現で CP932 と判定。どちらでもよい場合は設定の既定値（既定は CP932）。

### 3.3 EBCDIC の判別

EBCDIC は自動判別が難しいため、既定では候補に含めず、次のいずれかで選択します。

- ファイルタイプ設定（拡張子・フォルダパス規則）での指定
- 「文字コードを指定して開き直す」メニュー
- オプションで自動判別に含める場合: 0x40（EBCDIC の空白）の高頻度出現、0xC1〜0xE9（英大文字）、SO/SI の対応などでスコアリング

EBCDIC ファイルは改行を含まない固定長レコードであることが多いため、開く際に「レコード長」「改行コード（NL=0x15 / LF=0x25 / なし）」を指定できるダイアログを用意します。

## 4. 保存時の文字コード変換

詳細は [06-undo-backup-save](06-undo-backup-save.md) を参照。

1. 保存先文字コードの `Encoder` で全文を試験的にエンコード（書き出しと同時に行い、変換不能文字が見つかった時点で位置を記録）。
2. 変換不能文字があれば一覧ダイアログを表示（行・列・文字・コードポイント、ジャンプ可能）。
3. ユーザーが「中止 / 代替文字 / 数値文字参照 / エスケープ」を選択して保存。

### 4.1 変換時の文字の正規化オプション

| オプション | 例 |
|-----------|----|
| JIS/MS マッピング差の吸収 | U+301C（波ダッシュ）→ CP932 の 0x8160 に変換 |
| 互換文字の畳み込み | U+2460「①」を JIS X 0208 のみの Shift_JIS で保存する際に「(1)」へ |
| 半角カナ → 全角カナ | ISO-2022-JP（RFC 1468）で半角カナが使えない場合 |
| 改行コード変換 | CRLF / LF / CR / EBCDIC NL(0x15) |
| BOM の付加・除去 | UTF-8 / UTF-16 / UTF-32 |
